# 개발 기록에서 남긴 설계 교훈

이 문서는 Event Console 제작과 팀 내 시뮬레이션 중의 설계 판단을 공개 코드 기준으로 다시 정리한 기록입니다. 개발을 본업으로 하지 않는 제작자가 퇴근 후 시간을 이용해, 행사 콘솔 운영 경험이 없는 상태에서 개발했습니다. 아래 내용은 모든 기능의 현장 검증이나 완성도를 보장하지 않습니다. 미완성·미검증 부분이 있을 수 있으므로 후속 사용자는 자신의 행사에서 확인해야 합니다. 비공개 작업 기록이나 대화를 옮긴 연대기가 아니라, 개조할 때 참고할 이유와 검증 지점을 남깁니다.

## 공개 배포를 위해 이름과 설명을 일반화한 이유

특정 조직의 공식 결과물로 오해되지 않도록 프로젝트 이름을 **Event Console**, 저장소 이름을 `event-console`로 정하고 앱의 기본 브랜드 표기를 일반화했습니다. README에는 실제 제작 배경과 사용 사례로 조직·행사명을 언급하되, 제작자가 개인적으로 제작·공유하는 프로젝트임을 명시합니다. 고유 명칭 자체를 금지하는 것이 아니라 공식 제품·공식 배포물로 소개하지 않는 것이 표기 원칙입니다. 코드에 남아 있는 4팀 진행, 단계 잠금과 시상 순서는 원본 행사에서 사용한 규칙을 설명하는 예시이며, 모든 행사에 맞는 기본값이라는 뜻은 아닙니다.

확인된 Git 이력에서 콘솔 관련 변경은 2026년 8월 23일의 최초 커밋부터 9월 6일의 공개 정리까지 약 2주에 걸쳐 남아 있습니다. 이는 저장소에서 확인되는 기록 범위이며, 행사 전 개발에 연속으로 투입한 기간이나 총 작업 시간을 뜻하지 않습니다.

미디어 기능의 설명도 실제 설계 범위에 맞췄습니다. 숙련된 편집자가 사전 렌더 영상과 템플릿을 준비하고 리허설한 진행을 재생·전환하는 구조이며, MadMapper나 OBS 같은 범용 미디어 라우팅·방송 시스템을 목표로 하지 않았습니다. 문서 변경은 고유 명칭 잔존 여부, 상대 링크와 설명의 일관성을 정적으로 확인했습니다. 실제 미디어 재생 안정성은 이 문서 정리로 검증되지 않았으며 각 행사 장비에서 별도 리허설해야 합니다.

## 필요한 기능을 행사 흐름으로 묶어 보니 범위가 보였다

제작자가 필요하다고 정리한 큰 줄기는 스팅어, 라이브 중계, 음악 재생, 매치 팀 선택과 팀 정보 자동 출력, 중간 점수 표시, 승리 영상, 타이머, 라이브에서 스토리 장면으로의 전환이었습니다. 실제 행사 순서에 맞춰 정리하고 나니 생각보다 많은 종류의 기능이 필요하지 않았다는 것이 제작 소회입니다. 이는 구현이 간단했다거나 각 기능이 모든 환경에서 완성됐다는 평가가 아니라, 준비된 영상과 실시간 화면을 연결할 범위가 명확해졌다는 경험입니다.

후속 행사에 맞게 수정할 때에도 이 목록을 그대로 필수 사양으로 삼기보다는, 각 순서에서 관객에게 보여줄 화면과 운영자가 할 조작을 먼저 적어 보세요. 필요한 기능과 사전 제작할 미디어를 나누어 보면 기존 코드를 활용할 부분과 새로 준비할 부분을 정하기 쉽습니다.

## 조작 화면의 주인은 하나여야 한다

조작 화면과 송출 화면을 나누면 운영자는 다음 장면을 준비하면서 관객 화면을 독립적으로 확인할 수 있습니다. 그러나 조작 창을 두 개 열었을 때 둘 다 상태 요청에 답하면 늦게 온 오래된 상태가 송출 화면을 덮을 수 있습니다. 그래서 조작 창 사이에 단일 리더를 선출하고, 양도 직전에는 최신 상태를 저장·발행하며, 이전 리더의 늦은 heartbeat가 새 리더를 되돌리지 못하도록 epoch를 사용합니다.

동기화는 같은 origin의 `BroadcastChannel`을 기본으로 하고 `localStorage` 이벤트를 폴백으로 둡니다. 이 선택은 서버 없이 로컬에서 쓸 수 있게 하지만, 서로 다른 브라우저 프로필 사이의 동기화를 보장하지는 않습니다.

## 점수는 결과값보다 변경 이력이 중요하다

현장에서는 확정한 순위를 취소하거나 보너스를 되돌리는 일이 생깁니다. 팀별 합계만 저장하면 왜 그 점수가 되었는지 알 수 없고, 취소가 또 다른 실수로 이어지기 쉽습니다. 그래서 점수의 정본을 append-only 원장으로 두고 화면의 합계와 순위를 파생합니다. 취소도 기존 항목을 지우는 대신 반대 부호의 역분개 항목을 추가합니다.

배점이나 동점 규칙을 개조할 때에는 화면 숫자만 바꾸지 않고 원장 생성, 공동 순위 계산, 확정 취소와 표시 순위를 함께 검증해야 합니다.

## 전환 중에는 현재 화면보다 도착 화면을 기준으로 판단한다

장면 전환은 버튼을 누른 순간 끝나지 않습니다. 스팅어나 페이드가 화면을 덮고 컷 시점이 오기 전까지 상태에는 이전 장면이 남을 수 있습니다. 이 짧은 구간에 다음 큐를 실행하면 이전 장면을 기준으로 중복 전환을 만들거나, 끝난 영상의 늦은 이벤트가 운영자가 새로 고른 장면을 되돌릴 수 있습니다.

현재 구현은 전환이 끝나면 도착할 장면을 `pendingScene`으로 계산합니다. 전환과 재생 명령에는 단조 증가하는 세대 번호와 소유권을 두어 늦게 도착한 종료 이벤트가 더 새로운 조작을 완료 처리하지 못하게 합니다. 비동기 미디어 기능을 추가할 때에도 “누가 종료를 선언할 수 있는가”를 먼저 정하는 편이 안전합니다.

## 자주 바뀌는 값은 장면 전체를 다시 그리지 않는다

이 프로젝트의 작은 가상 DOM은 diff를 계산하지 않습니다. 직렬화한 HTML이 한 글자라도 달라지면 장면의 `innerHTML`을 교체합니다. 타이머나 오디오 미터처럼 매 프레임 바뀌는 값을 `view()` 결과에 넣으면 CSS 진입 애니메이션이 다시 시작되고 영상이나 카메라 노드가 교체될 수 있습니다.

따라서 장면의 구조는 `view()`에서 만들고, 시간에 따라 자주 바뀌는 텍스트와 스타일은 고정된 `data-bind` 슬롯을 `tick()`에서 갱신합니다. 새 실시간 표시를 만들 때는 상태 업데이트 빈도뿐 아니라 DOM 교체 여부까지 테스트해야 합니다.

## 비공개 단계는 마지막 출력 경계에서 잠근다

조작 버튼을 숨기는 것만으로는 아직 공개하면 안 되는 내용을 보호할 수 없습니다. 단축키, 큐시트, 저장 상태 복원처럼 장면에 들어가는 경로가 더 있기 때문입니다. 현재 구현은 잠긴 단계의 장면이 상태에 들어 있어도 최종 장면 선택에서 대기 화면으로 강등합니다.

행사 구조를 바꾸면서 비공개 단계를 추가한다면 조작 UI와 함께 렌더 경계의 허용 목록을 갱신해야 합니다. 테스트는 보이는 텍스트뿐 아니라 `alt`, `title`, `aria-label`처럼 화면에 노출될 수 있는 속성도 검사하는 편이 안전합니다.

## 상태 백업과 미디어 백업은 서로 다르다

운영 상태는 새로고침과 브라우저 재시작 뒤에도 살아야 하므로 JSON으로 직렬화할 수 있게 유지합니다. 영상과 사진 Blob까지 같은 상태에 넣으면 브라우저 저장 한도를 넘겨 전체 저장이 실패할 수 있어, 대용량 자료는 IndexedDB에 두고 상태에는 식별자와 메타데이터만 둡니다.

이 분리는 JSON 내보내기만으로 행사 미디어까지 백업되지는 않는다는 뜻입니다. 복구 절차는 상태 파일, 사용자가 등록한 미디어 원본, 필요한 폰트와 기본 자료를 각각 확인해야 합니다. 저장 스키마를 바꿀 때에는 정상 저장뿐 아니라 구버전 상태 정규화와 일부 저장소 실패도 함께 다룹니다.

## 미디어에는 우선순위와 소유자가 필요하다

같은 역할의 자료가 사용자 등록, 매니페스트, 기본 파일 등 여러 경로에서 올 수 있으면 “파일이 있다”만으로는 실제 송출 출처를 설명할 수 없습니다. 현재 구현은 출처의 우선순위를 정하고, 선택된 자료의 소유권과 object URL 정리를 추적하며, 더 이상 참조되지 않는 자료를 정리합니다.

공개 저장소에는 원본 행사 미디어가 없으므로 누락은 정상적인 초기 상태입니다. 새 자료를 추가할 때에는 권리 확인과 함께 파일 부재, 잘못된 형식, 재등록, 삭제 뒤 폴백을 검증해야 합니다. 폴백은 예측 가능한 안내 화면 또는 명시적인 사용 불가 상태여야 운영자가 원인을 바로 알 수 있습니다.

## 카메라와 리플레이는 기능 감지가 먼저다

카메라 권한, 캡처 장치, 코덱과 `MediaRecorder` 지원은 운영체제와 브라우저 조합에 따라 달라집니다. 지원되지 않는 기능을 정상 경로처럼 가정하면 현장에서 빈 화면이나 끝나지 않는 재생이 됩니다. 카메라 세션은 반복 요청에도 하나만 유지하고, 장치를 쓸 수 없으면 송출 화면과 조작 화면에 상태를 드러냅니다. 리플레이는 지원 가능한 형식을 고르고, 완성된 chunk만 재생 구간에 사용합니다.

자동 테스트는 선택 로직과 상태 전환을 검증할 수 있지만 실제 장치 권한, 드라이버, 캡처 해상도와 장시간 안정성까지 증명하지 못합니다. 사용할 장치 그대로 리허설하고, 실패했을 때 리플레이 없이 라이브 화면을 계속 운영할 절차를 준비해야 합니다.

## 오디오는 하나의 볼륨 값이 아니다

배경 음악, 영상 소리, master gain, ducking, 페이드, 브라우저 자동재생 잠금은 서로 다른 생명주기를 가집니다. 하나의 재생 버튼이나 볼륨 값에 모두 묶으면 장면 전환 뒤 음악이 돌아오지 않거나, 영상 종료가 새 음악 명령을 덮는 문제가 생깁니다. 현재 구현은 출력 축과 램프를 나누고 송출 화면의 오디오 잠금 상태를 조작 화면에 알립니다.

음악 목록은 사용자가 자신의 자료로 구성하는 영역입니다. 새 재생 규칙을 넣을 때에는 선택한 곡뿐 아니라 빈 목록, 자동재생 거부, 반복, ducking 도중 전환, 영상 오디오와의 조합을 확인해야 합니다.

## 자동 검사 통과와 현장 준비 완료는 다른 결과다

타입 검사와 단위 테스트는 점수 계산, 잠금, 저장 정규화와 비동기 상태 충돌을 빠르게 찾습니다. 빌드는 정적 파일이 만들어지는지 확인합니다. 그러나 실제 브라우저의 자동재생 정책, GPU 합성, 화면 배율, 장치 권한, 케이블, 오디오 라우팅과 캡처 지연은 현장 구성에서만 확인할 수 있습니다.
