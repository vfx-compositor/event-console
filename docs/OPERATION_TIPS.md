# 제작·운영 팁

원본 행사에서는 ProRes 4444로 출력한 알파 스팅어를 화면 위에 얹는 방식으로 연출을 구성했습니다. 이 문서는 그 제작 흐름과 코드에 남아 있는 설계 판단을 다른 행사에서도 응용할 수 있도록 정리한 것입니다. 개발을 본업으로 하지 않는 제작자가 퇴근 후 시간을 이용해, 행사 콘솔 운영 경험 없이 개인적인 판단과 팀 내 시뮬레이션을 바탕으로 만들었습니다. 따라서 아래 팁은 모든 환경에서 검증된 운영 지침이 아니며, 실제 행사 영상·음원·프로젝트 파일도 포함하지 않습니다.

아래 변환 명령과 설정값은 재현을 위한 예시입니다. 자신의 그래픽, 송출 컴퓨터, 브라우저와 음향 장비에서 확인한 값을 사용하세요. AI에게 수정 요청을 할 때는 [AI 수정 가이드](AI_CUSTOMIZATION.md)와 함께 전달하면 됩니다.

## 사전 영상 제작과 실시간 운영을 함께 준비하기

제작자는 행사 콘솔 운영 경험과는 별개로 영상 편집에는 숙련되어 있었으며, Envato 등의 템플릿·프리셋을 활용할 수 있는 작업 환경을 갖추고 있었습니다. 인트로, 종목 소개, 스팅어와 대기 영상 등 다양한 연출 자료를 미리 제작·렌더링하고, 현장에서는 준비한 영상 재생과 점수·타이머·카메라 등 실시간 출력의 교체를 함께 운영했습니다.

이 미디어 구조는 숙련된 편집자가 사전 렌더 영상과 템플릿을 준비하고, 정해진 진행표와 장비를 리허설한 통제된 환경에서 예상 범위의 재생·전환을 다루기 위해 만들었습니다. 임의의 입력과 효과를 현장에서 자유롭게 조합하는 MadMapper나 OBS 수준의 범용 라우팅·합성·방송 기능을 목표로 한 시스템은 아닙니다. 준비된 흐름 안에서도 브라우저 코덱, 장치, GPU와 오디오 경로에 따라 실패할 수 있으므로 실제 장비 리허설 없이 재생 안정성을 보장할 수 없습니다.

따라서 이 프로젝트를 다른 행사에 적용할 때는 콘솔 설정과 함께 **어떤 장면을 사전 렌더 영상으로 준비하고, 어떤 정보를 실시간으로 표시할지** 먼저 정하는 것이 좋습니다. 사용 가능한 편집 도구와 템플릿, 영상 제작 시간, 현장에서 바뀔 데이터를 기준으로 역할을 나누세요. 예시 영상에 보이는 완성된 연출에는 이 사전 제작 과정이 포함되며, 해당 행사 미디어 원본은 소스코드 배포에 포함하지 않습니다.

## 운영할 컴퓨터를 미리 정하기

실제 행사에서는 현장 노트북의 상태와 운영체제를 사전에 확인하기 어려워, 제작자가 본인의 맥북을 직접 가져가 콘솔을 운영했습니다. 준비에 사용한 컴퓨터를 그대로 사용해 운영체제와 설치 환경이 달라지는 변수를 줄이려는 선택이었습니다. 맥북이 필수 장비라는 뜻은 아니며, 이 프로젝트가 macOS를 중심으로 준비·확인된 배경입니다.

다른 행사에 적용할 때도 운영할 컴퓨터와 OS를 미리 확인하고, 그 컴퓨터에서 사용할 영상과 브라우저를 준비하세요. 개인 컴퓨터를 가져가더라도 현장 디스플레이·카메라·음향 장비와의 연결은 별도로 확인해야 합니다.

## 알파 스팅어 제작하기

스팅어는 장면 사이를 짧게 덮는 전환 영상입니다. 투명한 영역으로 기존 화면이 보이고, 그래픽이 화면을 가리는 순간 뒤쪽 장면을 바꾸면 전환을 자연스럽게 연결할 수 있습니다.

1. 편집·합성 도구에서 배경을 투명하게 만들고 RGB와 Alpha를 함께 출력합니다. ProRes 4444는 알파를 담을 수 있지만, 코덱 선택만으로 알파가 자동 생성되지는 않습니다. 출력 설정에서 알파 포함 여부를 확인하세요. [Apple ProRes 설명](https://www.apple.com/final-cut-pro/docs/Apple_ProRes.pdf)
2. 원본 MOV는 수정용 마스터로 별도 보관합니다. 브라우저에서 사용할 파생본은 VP9 알파 WebM으로 준비합니다. MOV 확장자를 업로드할 수 있다는 것과 해당 브라우저가 ProRes를 재생한다는 것은 별개의 조건입니다.
3. 목표 출력 해상도와 프레임레이트를 먼저 정합니다. 60fps 연출은 실제 송출 장치에서도 프레임 드롭 없이 재생되는지 확인하세요. 단순히 파일을 작게 만드는 것보다 실제 디코딩 부하와 전환 타이밍을 함께 보는 것이 중요합니다.
4. 밝은 배경과 어두운 배경 모두에 얹어 가장자리, 반투명 그림자, 모션 블러를 확인합니다. 검거나 흰 테두리가 생기면 원본 출력과 합성 단계의 straight/premultiplied alpha 해석을 점검합니다.

### FFmpeg 변환 예시

**ProRes 4444(Alpha 포함) MOV를 Chrome에서 사용할 때는 아래처럼 VP9 알파 WebM으로 변환한 뒤 등록하는 것을 이 프로젝트의 준비 절차로 삼습니다.** 원본 MOV를 전환 오버레이로 지정했지만 소리만 나고 영상은 보이지 않았다는 사용 사례가 있습니다. 재생 방식 선택은 브라우저의 코덱 지원을 바꾸지 않으며, 길이·오디오를 읽을 수 있어도 영상과 투명도까지 정상 디코딩된다는 뜻은 아닙니다.

먼저 `ffmpeg -version`과 `ffmpeg -h encoder=libvpx-vp9`를 실행해 설치 여부와 `yuva420p` 지원을 확인하세요. 없으면 [FFmpeg 공식 다운로드 안내](https://ffmpeg.org/download.html)에서 자신의 OS에 맞는 설치 방법을 선택합니다. FFmpeg는 아래 파일 변환에 필요하며 콘솔의 일반 실행 의존성은 아닙니다.

다음은 bash/zsh 등에서 실행하는 예시입니다. PowerShell에서는 줄 끝의 `\`를 쓰지 말고 명령을 한 줄로 합쳐 실행하세요. 파일명은 자신의 파일명으로 바꿉니다.

```bash
ffmpeg -i "stinger-master.mov" \
  -map 0:v:0 -map "0:a?" \
  -c:v libvpx-vp9 -pix_fmt yuva420p \
  -b:v 0 -crf 28 -deadline good -cpu-used 4 -row-mt 1 \
  -c:a libopus -b:a 128k -ar 48000 \
  "stinger.webm"
```

`yuva420p`의 `a`는 알파를 포함한다는 뜻입니다. 이 예시는 원본 해상도와 프레임레이트를 임의로 바꾸지 않고, 오디오가 있으면 Opus로 함께 변환합니다. 효과음이 필요 없다면 두 번째 `-map`과 오디오 인코딩 옵션 대신 `-an`을 사용하세요. CRF 28은 시작값이며, 가는 선·작은 글자·그라데이션을 보고 조정합니다. 배포용 WebM은 손실 압축 파생본이므로 ProRes 마스터를 대체하지 않습니다. [FFmpeg libvpx 옵션](https://ffmpeg.org/ffmpeg-codecs.html#libvpx), [VP9 알파 인코딩 구현 기록](https://ffmpeg.org/pipermail/ffmpeg-cvslog/2016-July/101177.html)

일반 H.264 MP4로 인코딩하면 알파가 유지되지 않습니다. 파일 확장자만 바꾸거나 `-c copy`로 MOV를 MP4에 재포장하는 작업도 영상 코덱을 변환하지 않으므로 ProRes 디코딩 호환 문제를 해결하는 방법이 아닙니다. 앱의 일반적인 MP4 변환 안내를 알파 스팅어에 그대로 적용하지 마세요.

알파 채널을 따로 확인하려면 투명·불투명 영역이 함께 있는 시점의 프레임을 추출합니다. 아래 `0.5`는 예시 시각(초)입니다.

```bash
ffmpeg -c:v libvpx-vp9 -i "stinger.webm" -ss 0.5 \
  -vf alphaextract -frames:v 1 "alpha-check.png"
```

검정은 투명, 흰색은 불투명, 회색은 반투명 영역입니다. 완전히 화면을 덮는 순간은 모두 흰색일 수 있으므로 한 프레임만 보고 알파 유무를 단정하지 마세요. VP9 디코더에 따라 알파가 보이지 않을 수 있어 입력 앞에 `-c:v libvpx-vp9`를 지정했습니다. 메타데이터만 확인하지 말고 최종 브라우저 합성 결과도 확인하세요. [FFmpeg VP9 알파 디코딩 이슈](https://ffmpeg.org/pipermail/ffmpeg-trac/2024-September/070729.html)

## 콘솔에 등록하고 전환 시점 맞추기

| 모드 | 사용할 때 | 확인할 점 |
| --- | --- | --- |
| `transition` | 앞 장면을 덮고 다음 장면으로 넘어가는 스팅어 | `switchAt` 시각에 그래픽이 장면 교체를 충분히 가리는가 |
| `overlay` | 현재 장면 위에 투명 그래픽을 얹기 | 뒤 장면을 유지하며 의도한 영역만 덮는가 |
| `full` | 영상 자체를 메인 화면으로 재생 | 종료 후 장면과 마지막 프레임 유지 여부가 맞는가 |

빠른 확인은 조작 패널의 `영상·에셋` 탭에서 등록합니다. **알파 채널을 자동 검사해 재생 방식을 정하지는 않습니다.** 새로 등록한 영상의 기본 방식은 `풀스크린`입니다. 각 카드의 **`▶ 재생 후 … · 큐 …`** 줄을 눌러 접힌 설정을 열고, `방식`에서 `전환 오버레이` 또는 `매치 알파 오버레이`를 직접 고릅니다. 카드 위쪽의 `풀스크린` 칩은 선택 버튼이 아니라 현재 방식의 표시입니다.

`전환 오버레이`를 선택하면 `씬 교체 시각(초)` 입력이 나타납니다. 스팅어로 사용할 장면 간 연결은 같은 탭의 `전환 할당`도 확인하세요. 재생 방식을 바꾸는 것은 투명한 픽셀을 새로 만드는 작업이 아니므로, 원본 파일에도 알파가 있어야 합니다. 브라우저 재생 실패 안내에 일반 MP4 변환이 표시되더라도, **알파를 유지해야 하는 영상은 위의 VP9 알파 WebM 변환 예시**를 따르세요. 관련 등록·설정 코드는 [tab-assets.ts](../src/control/tab-assets.ts)에 있습니다.

파일로 준비할 때는 WebM을 `public/media/`에 두고 `public/media/manifest.json`에 다음과 같이 등록할 수 있습니다.

```json
[
  {
    "file": "stinger.webm",
    "name": "장면 전환",
    "mode": "transition",
    "switchAt": 0.5,
    "after": "score",
    "revision": "stinger-v1"
  }
]
```

`switchAt`은 파일의 재생 시작 기준 **초 단위**이며, 전체 길이에 대한 비율이 아닙니다. 위 `0.5`는 예시일 뿐입니다. 화면을 완전히 덮는 프레임을 찾아 초로 환산하고 여유 구간을 두세요. `cueAfter`를 생략한 위 예시는 미디어를 등록하지만 진행 큐에 자동 삽입하지 않습니다. 실제 전환에 사용할 에셋 연결과 큐 구성은 행사 흐름에 맞게 설정·수정해야 합니다.

동일한 파일명으로 영상을 교체하면 `revision`도 변경합니다. 이 값이 바뀌어야 이미 등록된 브라우저가 새 파일을 가져오고, 명시한 새 타이밍도 반영할 수 있습니다. `npm run build` 후 실제 송출 창에서 파일과 타이밍이 함께 교체됐는지 확인하세요. 관련 계약은 [media-manifest.ts](../src/media-manifest.ts)에 있습니다.

## 재생·음향에서 확인할 것

- 첫 재생과 두 번째 재생을 모두 확인합니다. 예열은 재생 준비이며, 숨겨진 영상을 자동재생시키면 불필요한 디코딩과 프레임 드롭이 생길 수 있습니다. 이 때문에 [transition-video.ts](../src/transition-video.ts)는 `autoplay`를 끈 뒤 로드합니다.
- 스팅어 효과음은 기존 소리 위에 겹칠 수 있습니다. 원본 음량, 미디어 볼륨, 마스터 볼륨, 암전 상태를 함께 확인하세요. 현재 코드의 `TRANSITION_STINGER_GAIN`은 0.4 배율이며 dB 값이 아닙니다. 다른 행사에 맞게 바꿀 때 관련 테스트와 운영 메모도 함께 갱신합니다.
- 브라우저 자동재생 제한으로 소리가 막히면 송출 창에서 사용자 입력으로 오디오를 활성화합니다. 무음 영상이 보인다는 이유만으로 음향이 정상이라고 판단하지 마세요.
- 마지막 프레임 유지와 오디오 잔향 종료는 별도 동작입니다. `full` 영상의 `holdEndFrame`과 오디오 페이드 로직을 하나의 강제 정지로 합치면 검은 화면이나 갑작스러운 음향 단절이 생길 수 있습니다. [video-hold.ts](../src/video-hold.ts)
- 전환 중 연속 클릭, 다른 큐 선택, 암전, 파일 로드 실패도 시험합니다. 오래된 종료 이벤트가 다음 장면을 덮어쓰지 않는지 확인하세요. [scene-routing.ts](../src/scene-routing.ts), [transition-rules.ts](../src/transition-rules.ts)

## OBS로 송출·녹화하기

**콘솔에는 현장중계 라이브를 캡처·녹화하여 보관하는 통합 시스템이 없습니다.** 카메라 표시·리플레이와 행사 전체 녹화는 별개입니다. 아래 내용은 운영자가 외부 프로그램에서 따로 준비할 절차이며, 콘솔이 OBS 녹화 시작·종료나 파일 저장을 자동 관리하지 않습니다.

OBS를 사용하는 방송·녹화 구성이라면 **OBS Studio가 설치되어 있어야 합니다.** AI CLI는 먼저 사용자의 OS와 설치 여부를 확인하고, 없으면 [OBS 공식 다운로드](https://obsproject.com/download)를 통한 설치를 요구해야 합니다. 설치와 최초 실행이 끝난 후 캡처·음향 리허설을 진행합니다. 이 저장소의 런처는 OBS 설치나 실행을 자동 처리하지 않습니다.

기본 연결은 `콘솔 조작 창 → 같은 브라우저 프로필의 송출 창 → OBS 창 캡처 → 녹화/방송`입니다.

1. OBS를 실행하고 자신의 장비에 맞춰 초기 설정을 진행합니다.
2. Chrome/Edge에서 콘솔의 조작 창과 송출 창을 같은 프로필·같은 주소(origin)로 엽니다.
3. OBS에서 Windows/Linux는 창 캡처, macOS는 macOS 화면 캡처를 이용해 **송출 창**을 선택합니다. OS가 요구하는 화면 기록 권한을 허용하고, 잘림·해상도·커서 노출을 확인합니다. [OBS 시작 가이드](https://obsproject.com/kb/quick-start-guide)
4. 오디오 캡처 경로는 OS·OBS 버전·장치에 맞게 설정합니다. OBS 미터를 확인한 뒤 짧게 녹화해서 실제 파일의 소리를 들어봅니다. 데스크톱 오디오와 별도 앱 오디오를 중복 캡처하거나 모니터링 소리를 다시 입력받으면 이중 소리나 피드백이 생길 수 있습니다.
5. 스팅어, 음악, 마이크를 함께 재생하고 영상 싱크·피크·잔향을 확인합니다. 브라우저 창을 다른 창 뒤에 두는 실제 운영 배치에서도 재생이 유지되는지 확인합니다.
6. 실제 중계 기록이 필요하면 별도로 녹화를 시작하고, 저장 위치와 남은 용량을 확인합니다. 짧은 테스트 녹화를 종료한 뒤 파일을 다시 열어 영상·음성이 모두 저장됐는지 확인하세요.

**OBS의 브라우저 소스는 기존 Chrome/Edge 프로필과 별개의 실행 환경입니다.** 현재 콘솔은 `BroadcastChannel`과 브라우저 저장소로 동기화하므로 같은 URL을 넣는 것만으로 외부 조작 창의 상태를 받지 못합니다. 브라우저 소스를 직접 쓰고 싶다면 AI에게 서버 기반 통신 등 별도 동기화 설계를 요청하고, 자산 전달·재연결·상태 복구까지 검증해야 합니다. [현재 동기화 구현](../src/sync.ts)

콘솔 스팅어와 OBS의 장면 전환은 각각 별개로 실행됩니다. 한 번의 진행 명령에 두 전환이 겹치지 않도록 어느 쪽이 장면 교체를 담당할지 정하세요. 창 캡처 결과는 이미 합성된 화면이므로 원본 WebM의 알파 레이어 자체를 OBS에 전달하는 구성과도 다릅니다.

## 아이폰을 중계 카메라로 사용하기

실제 행사에서는 제작자가 카메라 연결에 필요한 **micro HDMI 케이블을 두고 와서 아이폰을 중계 카메라로 대신 사용했습니다.** Mac의 **연속성 카메라(Continuity Camera)** 기능으로 아이폰을 카메라 장치로 인식시킨 구성입니다. 예정한 카메라를 연결할 수 없을 때 스마트폰을 대체 입력으로 활용한 경험을 남깁니다.

이 방식은 AirPlay로 아이폰 화면을 미러링하거나, 중계 URL을 콘솔에 붙여 넣는 방식과 다릅니다. 콘솔은 브라우저가 인식한 카메라 장치를 선택해 사용합니다.

1. iPhone XR 이후 기종·iOS 16 이상, macOS Ventura 13 이상, 같은 Apple 계정과 이중 인증 등 [Apple의 지원 조건](https://support.apple.com/en-us/102546)을 확인합니다.
2. 아이폰에서 연속성 카메라를 활성화하고 Mac 가까이에 둡니다. 무선 연결을 사용할 때는 Wi-Fi·Bluetooth 등 Apple의 연결 조건을 확인하고, USB 연결에서는 아이폰이 Mac을 신뢰하도록 설정합니다.
3. 아이폰을 흔들리지 않게 거치하고 후면 카메라가 현장을 향하게 합니다. Apple 안내에 따라 아이폰을 잠근 상태에서 연결합니다. 장시간 촬영은 전원 연결과 발열도 점검하세요.
4. 콘솔의 `설정`에서 카메라 권한을 허용하고 장치 목록에서 아이폰 카메라를 선택합니다. 실제 촬영 위치에서 조작 창·송출 창의 영상과 화면 비율을 확인합니다.
5. 아이폰이 목록에 나타나지 않으면 지원 조건·연결 상태와 다른 카메라 사용 앱을 확인한 뒤 장치 목록을 다시 불러옵니다. Apple은 연결 문제 시 USB 연결 등을 안내합니다. [Apple 연속성 카메라 도움말](https://support.apple.com/en-us/102546)

연결 흐름은 `아이폰 카메라 → Mac 연속성 카메라 → 브라우저의 카메라 장치 → 콘솔 송출 화면`입니다. 이 카메라 입력 자체에는 OBS가 필수는 아니며, 방송·녹화를 OBS로 구성한다면 위의 OBS 설치·캡처·녹화 절차를 별도로 준비합니다.

### 현장에서 확인할 것

- 네트워크 혼잡, 영상 지연, 화면 회전, 배터리·발열, 잠금·통화 등으로 입력이 끊기는 상황을 리허설합니다. 연결이 끊겼을 때 대기화면으로 전환하고 다시 연결하는 순서도 준비합니다.
- 카메라 영상과 현장 마이크의 음향 경로를 각각 확인하고, 같은 소리를 두 번 받지 않도록 합니다.
- 장치·계정 식별자는 공개 문서에 넣지 않습니다. 자신의 비공개 운영 메모에 보관하세요.
- 아이폰 영상이 콘솔에 보인다는 사실이 녹화를 의미하지는 않습니다. 기록이 필요하면 OBS 등에서 별도 녹화를 시작하고 저장 파일까지 확인합니다.

덕분에 저는 1부 행사 동안 제 핸드폰을 사용할 수 없었습니다.
